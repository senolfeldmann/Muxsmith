## Authoring-time verification (2026-07-27): the experiment is settled, the mechanisms are vendor-verified

Everything in this section was verified on 2026-07-27 on the execution machine or at the named vendor source, per `proc-07-verify-against-source`. Tasks re-run the cheap confirmations (marked); they do not re-derive the rest.

**THE EXPERIMENT (item 2's route-picking question): an overlay config CAN clear an inherited key. Result: the CLEAR branch executes.**

- **Source level** (tag `tauri-cli-v2.11.4` on github.com/tauri-apps/tauri, the repo-pinned CLI version; `crates/tauri-cli/src/helpers/config.rs`, fn `load_config`): the platform file `tauri.<platform>.conf.json` is applied to the base config with `json_patch::merge` - RFC 7396 JSON Merge Patch, **a `null` value DELETES the key**. `-c` overlay files are first combined null-PRESERVING (fn `merge_patches`, whose doc comment reads "Same as `json_patch::merge` but doesn't delete the key when the patch's value is `null`") and then applied to the config with the same deleting `json_patch::merge` - so BOTH levers clear. Schema validation runs on the post-merge document, where the cleared key is simply absent.
- **Empirical, this machine, repo-pinned CLI 2.11.4** (config merging is a CLI concern; only the dmg bundling needs macOS): baseline `./node_modules/.bin/tauri bundle -d --bundles deb` produced a deb whose control file shows `Recommends: mkvtoolnix`. With a test file `src-tauri/tauri.linux.conf.json` containing `{"bundle": {"licenseFile": null, "linux": {"deb": {"recommends": null}}}}`, the identical re-bundle produced a control file with **no Recommends line at all** (`dpkg-deb -I ... | grep -cE '^ Recommends'`: 1 before, 0 after; `Depends: libwebkit2gtk-4.1-0, libgtk-3-0` intact as the positive control) and the null-carrying config **passed the CLI's schema validation**. The absence result is fire-verified by construction: the same grep invocation returned 1 on the baseline minutes earlier. Test file and bundle output removed afterwards; tree clean.
- Consequence: the owner's preferred route (drop the license for macOS only, keep Windows) needs **no contortion** - one committed 3-line platform file, zero workflow changes - so the pre-decided tiebreaker never fires. The fallback branch remains fully specified in Task 2 with enumerated switch triggers, so no second planning round is needed under any outcome.

**Ad-hoc signing (item 1's mechanism), verified at the vendor's current documentation** (v2.tauri.app/distribute/sign/macos, fetched 2026-07-27): Tauri documents ad-hoc signing via the **pseudo-identity `-`** in `tauri.conf.json > bundle > macOS > signingIdentity` (or `APPLE_SIGNING_IDENTITY`), and states that "Ad-hoc code signing does not prevent MacOS from requiring users to whitelist the installation in their Privacy & Security settings" - exactly the flow `docs/INSTALL.md` documents. No Apple account, certificate or notarization involved. The pinned CLI's own bundled schema (`node_modules/@tauri-apps/cli/config.schema.json`) carries `signingIdentity` typed `["string","null"]`; the red state of a wrong-typed value is real: with `signingIdentity: 123`, `./node_modules/.bin/tauri inspect wix-upgrade-code` exits 1 with `error on 'bundle > macOS > signingIdentity': 123 is not of types "null", "string"` (observed 2026-07-27), and exits 0 on the restored config.

**dmg license mechanism, verified at the pinned bundler source** (`crates/tauri-bundler/src/bundle/macos/dmg/mod.rs` + `bundle_dmg` + `eula-resources-template.xml`, tag `tauri-cli-v2.11.4`): the dmg attaches a pre-mount license **only if** `settings.license_file()` is Some (`--eula` argument); the EULA rides as classic `LPic`/`STR#` resources (plain-XML plist keys around base64 data, attached via `hdiutil udifrez`); a plain-text file becomes a `TEXT` resource, a file that `file -b` reports as `Rich Text Format data` becomes an `RTF ` resource. Clearing `licenseFile` therefore removes the entire resource block - the defect class disappears rather than being repaired (the ROADMAP entry's own analysis). Default dmg filesystem is HFS+ (script help), so Linux-side `7z` inspection works, as the original R8 Linux-side measurement already demonstrated.

**License-key surface re-confirmed at the pinned schema:** `license` and `licenseFile` appear exactly once each in `config.schema.json`, both in the global `bundle` object - no Dmg/Wix/Nsis/Deb/Rpm/AppImage section carries a license property. `LICENSE` line 3 carries `Ş` as UTF-8 `c5 9e` (hexdump-verified; note for check authors: a plain `grep -P '\xc5\x9e'` does NOT match raw bytes in a UTF-8 locale - it silently returns nothing, observed at plan-authoring - use hexdump or `LC_ALL=C` forms).
