# Plan 5.8 decisions

## D38: zero-rule-keep passthrough - PassthroughProfile info diagnostic

**Decision:** a profile with empty `tracks.rules` and `tracks.unmatched:
keep` is a LEGAL pure-passthrough remux: use it to change only title /
attachments / chapters, or to normalize the container, without any track
rule. Empty rules with `unmatched: drop` (the default,
model.rs:306-307/:314-316) stays a `NoTrackRules` error. Owner ruling
2026-07-13 (escalation resolution, session 10), recorded in
`docs/product-boundaries.yaml` `core-83-zero-rule-keep-passthrough`
(:388-402); the decision set below was owner-approved 2026-07-14.
core-83's statement, quoted:

> A zero-rule profile with tracks.unmatched=keep is a LEGAL
> pure-passthrough remux (all primary tracks copied; use it to change
> only title / attachments / chapters, or to normalize the container,
> without any track rule). With tracks.unmatched=drop, zero rules stays
> a NoTrackRules error. MUST be documented and hinted - the passthrough
> path via unmatched=keep is non-obvious. (Şenol ruling, escalation
> resolution, session 10.)

Mechanics:

- `validate.rs` lifts the unconditional error (the
  `profile.tracks.rules.is_empty()` emitter at
  crates/muxsmith-core/src/profile/validate.rs:61-63) only for the keep
  case. The keep case instead emits a NEW info-severity diagnostic
  `DiagCode::PassthroughProfile` (variant added to the `DiagCode` enum,
  crates/muxsmith-core/src/report/mod.rs:42; config_path `tracks.rules`,
  no params) at validate time, confirming the profile is a deliberate
  passthrough - an accidental delete-all-rules edit stays visible.
  Note `rules` has no serde default (model.rs:311), so the idiom is
  written explicitly: `tracks: { unmatched: keep, rules: [] }`.
- The `no-track-rules` catalog message gains a pointer hint. Current
  strings, quoted exactly:
  - locales/en/diagnostics.ftl:7: `no-track-rules = The profile defines
    no track rules; at least one is required.`
  - locales/de/diagnostics.ftl:14: `no-track-rules = Das Profil
    definiert keine Spurregeln; mindestens eine ist erforderlich.`

  Proposed replacements (PROPOSAL, for owner wording review):
  - en: `no-track-rules = The profile defines no track rules; add at
    least one rule, or set tracks.unmatched: keep for a pure passthrough
    remux.`
  - de: `no-track-rules = Das Profil definiert keine Spurregeln; füge
    mindestens eine hinzu oder setze tracks.unmatched: keep für einen
    reinen Passthrough-Remux.`
- Bilingual catalog entries for the new `passthrough-profile` message
  (PROPOSAL, for owner wording review):
  - en: `passthrough-profile = This profile defines no track rules and
    tracks.unmatched is keep: a pure passthrough remux; every primary
    track is copied unchanged. If this is not intended, add track
    rules.`
  - de: `passthrough-profile = Dieses Profil definiert keine Spurregeln
    und tracks.unmatched ist keep: ein reiner Passthrough-Remux; alle
    Spuren der Primärquelle werden unverändert übernommen. Falls das
    nicht beabsichtigt ist, füge Spurregeln hinzu.`
- README gains a short passthrough recipe subsection. Placement
  (PROPOSAL): a new `###` subsection at the end of "How it works"
  (README.md:23), after the dry-run/run paragraph and before "What you
  get" (README.md:67). Content: the `unmatched: keep` + `rules: []`
  idiom and the three use cases (change only the title; attachment /
  chapter surgery; normalize the container). The GUIDE version lands at
  1.0 with the GUIDE itself, not now.
- Tests the plan must carry:
  - validate_semantics cases
    (`crates/muxsmith-core/tests/validate_semantics.rs`): keep + zero
    rules -> `PassthroughProfile` info, no `NoTrackRules` error;
    drop + zero rules -> `NoTrackRules`
    error (the existing assertion at validate_semantics.rs:54 covers the
    default-drop shape today).
  - catalog_completeness `fixture_args` entry for the new code (the
    exhaustive match fails to compile until it is added,
    crates/muxsmith-cli/tests/catalog_completeness.rs:32-47).
  - An end-to-end dry-run + run of a zero-rule-keep profile proving the
    executor path: the D20 "passthrough counts as matched" machinery
    already exists (spec 4.5 track-order prose), and spec 5.2's
    `EmptyPlan` row (v1-design.md:266) already exempts a keep plan whose
    primary carries at least one track.

**Rationale:** owner ruling 2026-07-13 (escalation resolution, session
10; recorded in product-boundaries.yaml core-83). The executor path has
existed since D20: kept-but-unmatched primary tracks count as matched,
so a zero-rule keep plan is a working remux today - only the validate
gate forbids writing it. core-83 mandates "MUST be documented and
hinted" because the passthrough path via `unmatched: keep` is
non-obvious; the hint in `no-track-rules` (the error IS the discovery
moment) plus the README recipe satisfy that. Info severity is the
calibrated middle: the sanctioned use case is confirmed, not nagged,
while an accidental rule deletion still surfaces in every validate /
dry-run report.

**Rejected alternatives:**
- Keep erroring under keep: contradicts the owner ruling; it was exactly
  the superseded D20 assumption. Rejected.
- Warning severity for the new diagnostic: nags the sanctioned use case
  on every run of a deliberate passthrough profile. Rejected.
- Silently legal with no diagnostic: an accidental delete-all-rules edit
  becomes invisible, and core-83 mandates the hint. Rejected.
- GUIDE-only documentation: the GUIDE lands at 1.0; until then the
  `no-track-rules` error message is the discovery moment, so the hint
  must live there (and in the README). Rejected.

**Interface/wire-format change:** new `DiagCode::PassthroughProfile`
value (info severity) on the diagnostics JSON surface: code +
config_path `tracks.rules`, no params; bilingual catalog entries; spec
section 5.2 gains its row. No existing code's wire shape changes; the
`no-track-rules` message change is catalog wording only (no param
change).

**Supersedes:** the D20 "Open mechanics (plan-time)" marked assumption
in `docs/superpowers/specs/2026-07-09-plan-3.5-design-decisions.md`
:156-160 ("Zero rules under `keep`. Today zero rules is `NoTrackRules`
error (H12). Assumption: still an error ... contradict if a pure
passthrough profile should be legal."). The contradiction arrived as the
2026-07-13 owner ruling; the Plan 5.8 execution adds a "superseded by
D38" annotation at that spot in the plan-3.5 file.

**Spec amendments** (named here; the edits are Plan 5.8 execution
tasks on `2026-07-08-muxsmith-v1-design.md`):
- 4.5 (:178-192): state zero-rules legality under keep - `tracks.rules`
  may be empty when `unmatched: keep` (pure passthrough); empty rules
  under `drop` remain a `NoTrackRules` error.
- 5.2: new `PassthroughProfile` row (info severity) in the diagnostics
  table.
- 5.4: checked the actual wording - the static-lint prose (:299)
  enumerates regex/template compilation, type errors, unknown
  properties, closed-domain checks, exact-only, and provable overlaps;
  it contains no "at least one rule" clause and does not name the
  rules-non-empty check at all (that wording lives only in the catalog
  message, locales/en/diagnostics.ftl:7, amended above). No 5.4 edit is
  required; if the plan adds the rules-presence check to 5.4's
  enumeration, it enters as policy-dependent (`unmatched: drop` only)
  from the start.
- Per the ADR convention, the execution plan carries a
  self-contradiction sweep over the spec: no other section may keep
  stating an unconditional rules requirement.

**Triggers created:** none.

**Consistency note:** mkvtoolnix comparison (SI-3): MATCH.
`mkvmerge -o out.mkv in.mkv` copies all tracks by default; a passthrough
remux is mkvtoolnix-gui's trivial base case (open a file, change
title/attachments/chapters, mux). Declarative Muxsmith needs an explicit
profile idiom for the same operation, and that idiom is
`unmatched: keep` + zero rules; legalizing it matches mkvmerge's default
semantics instead of diverging from them.

## D39: allowed-param wire cleanup + invalid-property-value catalog selector

**Decision:** the English-prose `allowed` param leaves the wire for
language emissions; the catalog discriminates on the existing
`$property` param instead.

- Catalog-side: `invalid-property-value` (en + de) becomes a Fluent
  select on `$property`: a `[language]` arm rendering
  registry-membership wording WITHOUT `$allowed`, and the default
  `*[other]` arm keeping the current allowed-list wording. Current
  strings, quoted exactly:
  - locales/en/diagnostics.ftl:43: `invalid-property-value = Value
    "{ $value }" is not valid for property "{ $property }". Allowed
    values include: { $allowed }.`
  - locales/de/diagnostics.ftl:50: `invalid-property-value = Der Wert
    "{ $value }" ist für die Eigenschaft "{ $property }" nicht gültig.
    Zulässige Werte sind unter anderem: { $allowed }.`

  Proposed bodies (PROPOSAL, for owner wording review):

      invalid-property-value = { $property ->
          [language] Value "{ $value }" is not valid for property "language"; it must be a valid ISO 639 or BCP-47 language code.
         *[other] Value "{ $value }" is not valid for property "{ $property }". Allowed values include: { $allowed }.
      }

      invalid-property-value = { $property ->
          [language] Der Wert "{ $value }" ist für die Eigenschaft "language" nicht gültig; er muss ein gültiger Sprachcode nach ISO 639 oder BCP-47 sein.
         *[other] Der Wert "{ $value }" ist für die Eigenschaft "{ $property }" nicht gültig. Zulässige Werte sind unter anderem: { $allowed }.
      }

- Core-side: the two planner.rs emitters stop sending the
  English-prose `allowed` param "a valid ISO 639/BCP-47 language code":
  `walk_exact_languages` (crates/muxsmith-core/src/planner.rs:440-448,
  the param at :447) and `resolve_changes` (:811-824, the param at
  :822). property=language emissions carry `property` + `value` only.
  The validate.rs closed-domain emitter (type/codec_kind,
  crates/muxsmith-core/src/profile/validate.rs:274-289) is unchanged:
  its `domain_hint` lists are locale-neutral value tokens, not prose.
- The stale emitter-site comment at planner.rs:819-821, quoted:
  "`invalid-property-value` requires `allowed`; the sibling emitter in
  `walk_exact_languages` sets it, so this site must too or `{$allowed}`
  leaks to the user." - justifying the param at :822 - is updated to
  describe the selector.
- Test topology the plan must carry: the `fixture_args` entry for
  `InvalidPropertyValue`
  (crates/muxsmith-cli/tests/catalog_completeness.rs:63-67, today
  property "language" + the prose `allowed`) switches to the `*[other]`
  arm (e.g. property "type" with a real allowed list) so the list-arm
  `{ $allowed }` placeholder stays fixture-guarded; the existing
  site-level leak test
  `invalid_changes_language_diagnostic_renders_without_placeholder_leak`
  (catalog_completeness.rs:397, doc comment :387-395), which renders the
  REAL `resolve_changes` emitter output through `plan_batch`, pins the
  `[language]` arm. Both arms covered while respecting the documented
  single-fixture-per-code limitation (catalog_completeness.rs:39-47).
  The comment update extends to the two catalog_completeness.rs
  narrations this ADR cites, which the same change would otherwise leave
  describing an inverted reality: the limitation text at :43-47 ("The
  one known instance ... is fixed and pinned by ...") and the leak-test
  doc comment at :392-395 ("Before the fix that added
  `.with("allowed", ...)` ...") - after D39 the `allowed` param is
  deliberately absent from both emitters and the leak test pins the
  `[language]` arm, so the execution plan sweeps both narrations in the
  same diff.

**Rationale:** pre-1.0 whole-branch finding I2 (tracked as the
"Mixed-language `allowed` param" pre-1.0 gate, docs/ROADMAP.md:186-192):
in de mode `invalid-property-value` renders mixed German/English because
core passes user-facing English prose in a param. That violates spec 5.2
(v1-design.md:255, "Core emits no user-facing prose") and is absent from
the 8.4 accepted-exception list (:397), so it is a defect, not an
allowance. Selecting on the existing `$property` param closes the gap
with no new wire element: the param already discriminates the language
emissions from the type/codec_kind ones.

**Rejected alternatives:**
- A new `allowed-kind` wire param: adds a wire element where an existing
  param already discriminates the arms. Rejected.
- A new dedicated DiagCode for invalid language values: heavier wire
  change, new catalog keys and fixtures in both locales, no benefit over
  the selector. Rejected.
- Keep sending the prose param unused by the catalog: dead English prose
  on the JSON wire; the spec 5.2 violation stays. Rejected.
- Amending the 8.4 exception list to legalize the prose: treats the
  symptom and contradicts the prose-free-core architecture. Rejected.

**Interface/wire-format change:** a param REMOVAL on the diagnostics
JSON surface: property=language emissions of `invalid-property-value`
lose `allowed` and carry `property` + `value` only; type/codec_kind
emissions are unchanged (real value list via `domain_hint`). Pre-1.0, no
compatibility promise.

**Spec amendments** (named here; the edits are Plan 5.8 execution
tasks):
- 5.2 `InvalidPropertyValue` row: checked the actual row text
  (v1-design.md:281) - it names no params and no `allowed`, so no row
  edit is required.
- 8.4 needs NO change: the prose leaves core instead of being excepted,
  so the exception list stays as-is and the 5.2 prose-free-core sentence
  (:255) holds again once the change lands.

**Triggers created:** none new. Consumed: the ROADMAP Triggers entry
(docs/ROADMAP.md:85-87) "Any change to diagnostic wire params or
NUMERIC_DIAGNOSTIC_PARAMS -> fix the diagnosticFluentParams.ts
strictness comment (or implement /^\d+$/) (routed-items item 7)" FIRES
with this change and is consumed by Plan 5.8: the same diff fixes the
strictness doc comment (src/diagnosticFluentParams.ts:19-27, whose claim
"rejects negative numbers, floats, empty strings, and scientific
notation" at :25-26 overclaims - the `Number()` + `Number.isInteger`
check at :46-48 accepts scientific notation that normalizes to an
integer, e.g. `Number("1e3") === 1000` passes) or implements the
`/^\d+$/` guard. Recorded here as fired-and-consumed.

**Consistency note:** mkvtoolnix comparison (SI-3): mkvtoolnix ships
fully localized catalogs; a mixed-language diagnostic render is a
genuine gap against that bar, and closing it is a MATCH, not a
divergence.
