## D19: BCP-47 language values are validated by well-formedness, not ISO-membership (fixes a bug)

**The bug.** Spec 4.4 says language values are BCP-47. The implementation builds
`LanguageIndex` solely from `mkvmerge --list-languages`, whose table is ISO
639-1/2/3 codes only. A full IETF tag with a region or script subtag - `pt-BR`,
`de-DE`, `es-419`, `zh-Hans`, `sr-Latn` - has no row, so `normalize()` returns
`None`. Consequence:
- `changes: { language: pt-BR }` -> hard `InvalidPropertyValue` at plan time,
  even though `mkvmerge --language 0:pt-BR` is valid and writes a `LanguageIETF`
  element (mkvmerge man page: "--language ... IETF BCP 47"; example
  `sr-Cyrl-RS`). This is the hard failure: a regional/script language cannot be
  SET at all.
- `exact: { language: pt-BR }` currently "works" only by the raw-string fallback
  (matcher.rs, unrecognized token -> case-insensitive string compare), which is
  fragile (misses `pt-Latn-BR` vs `pt-BR` canonicalization).

mkvtoolnix parity: the GUI reads and writes `language_ietf` and accepts any
BCP-47 tag; our audience uses regional tags routinely. This is squarely a
muxing-semantics gap (not an interactive-convenience one), so it is a parity
target and, given the spec already promises BCP-47, a bug.

**Decision.**
- **Acceptance = well-formedness.** A language value is valid if it is either a
  bare ISO code already in the language index (unchanged path, so `de`==`ger`
  keeps working) OR a well-formed BCP-47 language tag
  (`language[-script][-region][-variant...]`, canonical casing irrelevant).
  Grammatically-well-formed-but-nonexistent combinations (e.g. `xx-YY`) are
  accepted here and left for mkvmerge to reject at mux time; over-accepting a
  pathological tag is far less harmful than today's over-rejecting of real ones,
  and matching mkvmerge's exact registry cheaply is not possible per-tag.
- **Equality for matching = canonical form via `canonicalize()`.** Bare ISO
  codes compare via the existing 639-3 canonical key. Tagged values compare by
  BCP-47 *canonical form* using the crate's `canonicalize()` (case
  normalization + script suppression + deprecated-subtag replacement, from the
  IANA subtag registry the crate bundles at build time), so `pt-Latn-BR`==`pt-BR`
  (redundant default script dropped) and `iw`==`he` (deprecated code replaced),
  while meaningful distinctions are preserved: `pt-BR`!=`pt-PT`,
  `zh-Hans`!=`zh-Hant`, `sr-Cyrl`!=`sr-Latn`. Raw case-insensitive compare stays
  the fallback when a value does not canonicalize. The matcher reads both
  `language` and `language_ietf` from `-J`, so a bare-code rule still matches a
  tagged track via its legacy `language` field.
- **Accept-liberal, match-precise (deliberate asymmetry).** The accept side
  (validation) uses `parse()` well-formedness only: a well-formed but
  nonexistent tag (`xx-YY`) is accepted and left for mkvmerge to reject at mux
  time (registry `validate()` is NOT called). The match side uses
  `canonicalize()`. Coherent: `exact: {language: xx-YY}` then never matches any
  real track (nothing canonicalizes to it), which is harmless.
- **Validation points unchanged:** `changes.language` and match values, both at
  plan time (per D2/D10). Only the predicate changes (well-formed-BCP-47-or-ISO,
  not in-ISO-index).

**Principle (README/guide-worthy, Şenol 2026-07-09).** Muxsmith's `exact`
operator is *typed value-equality, not raw string equality*: each property is
compared in its own domain. Numbers compare numerically (`6`==`6.0`); languages
compare as languages, ISO spellings and BCP-47 tags reduced to canonical form
(`de`==`ger`, `pt-Latn-BR`==`pt-BR`) while meaningful distinctions survive
(`pt-BR`!=`pt-PT`). Byte-literal matching remains available via `regex`. This is
one of the tool's core semantics; surface it in the public docs at 1.0. Task 5
writes it into spec 4.3.

**Resolved (Şenol 2026-07-09).** Use the `language-tags` crate (pure Rust, RFC
5646, bundles the IANA registry): `parse()` for accept-side well-formedness,
`canonicalize()` for match-side canonical equality. Correctness on a standard
grammar beats a hand-rolled parser; one vetted dependency (through `cargo deny`)
is justified. Regression guard: all existing ISO-code match/validation tests
must stay green.

## D20: `unmatched_tracks: keep | drop` policy, default `drop`

**Why.** Muxsmith drops every track no rule matched (spec 4.9 asymmetry note);
mkvtoolnix keeps all tracks and the user subtracts. Default stays `drop` - that
IS Muxsmith's declarative essence and its primary (curative) use case. But
`drop`-only makes *additive* bulk operations inexpressible: "add a German
external subtitle to every file, keep everything else" cannot be written when
per-file track layouts vary, because the one-track-per-rule invariant (spec 2,
B1) forbids a catch-all "keep all remaining audio" rule (that is `AmbiguousRule`)
and `optional` only tolerates zero matches, not many. `keep` is the only
mechanism that expresses passthrough-of-the-unaddressed. This mirrors the
`attachments.unmatched` policy the spec already has (which even defaults to
`keep`); tracks get the same policy with the opposite default.

**Decision.**
- `tracks` is restructured from a bare rule list into a `{ unmatched, rules }`
  block, matching the existing `attachments` block and the profile's
  established "policies live in their section" language (`output.on_collision`,
  `tags.global`/`tags.track`). New field `tracks.unmatched: keep | drop`,
  default `drop` (current behavior preserved when omitted). `attachments` is
  already `{ unmatched, rules }` and does not change; only `tracks` moves.
  Breaking format change, free pre-release: update model, fixtures, tests, the
  generated JSON schema (schemars, automatic), and the spec 4.1/4.5 text.
- **`drop` (default):** unchanged - only rule-matched tracks survive.
- **`keep`:** every source track of the PRIMARY is retained and the primary is
  preserved as-is. Rule-matched primary tracks additionally get their `changes`
  applied but do NOT reposition (reordering the primary is a `drop`-mode
  operation). Command generation drops the per-kind `--*-tracks`/`--no-*`
  restriction for the primary (mkvmerge keeps all by default). Track order: see
  the resolved decision below (primary tracks first in source order, donors
  trailing).
- **Donors and attachments are unaffected.** The policy governs the primary's
  own tracks only. A donor file is opened solely for its rule-selected track
  (its group already gets `--no-attachments` etc.); "keep unmatched donor
  tracks" is never wanted (it would pull in the donor's video/subs). Mirrors the
  primary-only scope of attachment rules (D10/E5).

**Track order under `keep` (RESOLVED B, Şenol 2026-07-09; reverses the earlier
assumption).** `--track-order` lists ALL primary tracks first, in the primary's
source order (id ascending), then donor tracks in profile-rule order. So the
additive case ("add a German sub, keep the rest") renders `[video, audio, ...,
sub]` with no extra rules.

Şenol's reasoning (the load-bearing reframing): "keep = match to what is
already there", so a kept-unmatched primary track IS a matched track;
therefore listing it in `--track-order` does not violate the "only matched
tracks appear in `--track-order`" invariant - the invariant holds intact. And
the primary file is primary, i.e. first; donors trail.

The earlier assumption (matched-ordered-first, unmatched-appended-after)
produced donor-FIRST ordering for a donor-only keep profile - the added
subtitle landed ahead of the primary's video/audio, which the Plan 3.5
whole-branch review flagged (verified against mkvmerge v100: `( primary[P0,P1] )
--subtitle-tracks 0 ( donor[D] ) --track-order 1:0` -> `[D,P0,P1]`) as
unintuitive on the exact use case `keep` exists for. B fixes it.

Consequence (the one point held open for veto, not vetoed): explicit primary
rules under `keep` change properties, not position; to reorder the primary, use
`drop` mode (which lists tracks in the wanted order). Implementation: the `Plan`
carries the primary's full track-id list in source order; under `keep`,
`command` emits those as `0:id` first, then donor assignments as `g:id`.

**Open mechanics (plan-time).**
- **Zero rules under `keep`.** Today zero rules is `NoTrackRules` error (H12).
  **Assumption: still an error** (a zero-rule profile is almost certainly a
  mistake, even though `keep`+zero-rules is a semantically valid no-op remux);
  contradict if a pure passthrough profile should be legal.

## D21: clean unsupported-source diagnostic (fixes B17)

**The problem.** A source mkvmerge identifies with exit 0 but reports as
unrecognized/unsupported container or zero tracks passes identification; the
planner never consults `is_identifiable()` and falls through to per-rule
`MissingTrack` errors. The user sees "rule X: missing track" when the real cause
is "this file is not a source mkvmerge can mux." (The existing
`UnidentifiableSource` covers only the mkvmerge-EXIT-NONZERO case.)

**Decision.**
- After identification, before rule resolution, gate on `is_identifiable()`
  (identify.rs). A source that is not usable media emits one clear
  error-severity diagnostic and its plan is skipped, exactly like other
  error-severity file diagnostics (spec 5.1).
- **New code `UnsupportedSource`**, distinct from `UnidentifiableSource`: the
  latter stays for mkvmerge exit-nonzero (detail carries the error), the former
  is "mkvmerge identified it but it is not a muxable source." Two codes because
  the remediation differs. New Fluent message under `locales/`.

**Open mechanic (plan-time).** Exact trigger predicate. **Assumption: fire
`UnsupportedSource` when `!container_recognized || !container_supported`; a
recognized+supported container with zero tracks stays a per-rule `MissingTrack`
issue** (it is a valid but empty container, a different problem, and the
zero-track empty-plan warning is a separate deferred item - recorded in D18,
promoted 2026-07-11 to a pre-1.0 gate in `docs/ROADMAP.md` with the options
variant in `docs/IDEAS.md` #5; this sentence originally pointed at IDEAS.md
before any entry existed there). Contradict if zero-track sources should also
be `UnsupportedSource`.
