## Findings

### Finding 1 (Important): the README's new passthrough recipe crashes `muxsmith run` on the merged tree - pre-existing `Plan` JSON serialization panic, newly steered into by this branch's documentation

- **Evidence:** README.md:69-78 (the recipe, with `title: { template: 'S{season}E{episode}' }` at :77) run verbatim: the mux succeeds (output verified: 2 tracks, title `S01E01`), then the process panics and exits 101: `panicked at crates/muxsmith-core/src/report/json.rs:44: cannot serialize tagged newtype variant TitleAction::Set containing a string`. `dry-run --json` on the same recipe panics identically (against README.md:91's "every command takes `--json`"). `dry-run` human mode is unaffected; a title-less passthrough profile (the e2e's shape) is unaffected in all modes.
- **Root cause (pre-existing, outside the range):** `TitleAction` (crates/muxsmith-core/src/planner.rs:110-118) is `#[serde(tag = "kind")]` with the newtype variant `Set(String)`; serde's internally-tagged representation cannot serialize a newtype variant whose payload is not map-shaped, and `report/json.rs:44` unwraps. `run` hits it even without `--json` because `run.rs:274-275` builds `run_document(batch_document(...))` unconditionally for the persisted run report - which also means the D26 per-job run document is never persisted for such runs. The enum region and json.rs are byte-identical at merge base ed727af (verified) and the range diff touches neither file's relevant code; no existing test ever serializes a `Set` plan (grep: tests use only `Keep`/`Clear`). Same latent shape, expected to fail identically though not exercised here: `ChapterSource::External(PathBuf)` (planner.rs:90-97) and `PrimaryAttachments::Subset(Vec<u64>)` (planner.rs:125-132) - i.e. external chapters and attachment select-subsets should crash `run` the same way. As a product defect this is Critical-class (exit code lies after a successful mux; three spec-4.9 features affected); as a whole-branch finding it is Important because the branch's own code is correct and the defect predates it - but the branch's mandated documentation (core-83 "MUST be documented") now promises, as the README's flagship passthrough use case, a flow that crashes the binary, and the plan's own step required the recipe to be paste-runnable.
- **Suggested fix:** not a README edit - the recipe is core-83's mandated documentation and correct as a promise; the binary must honor it. Fix the serde representation of the three enums (struct variants, e.g. `Set { title: String }` / `External { path: PathBuf }` / `Subset { ids: Vec<u64> }`, or adjacent tagging `#[serde(tag = "kind", content = "value")]`); no working consumer of the current shape can exist (it never serialized without panicking), so pre-1.0 the shape choice is free - but it is a diagnostics/report wire-format decision, hence ADR-gated per house process: route as a small follow-up ADR + fix task before plan close, with a regression e2e that drives the README recipe verbatim through `run` and `dry-run --json` (pinning both the bug and the recipe's paste-runnability).

No Critical findings within the branch's own changes. No other Important or Minor findings: cross-stream semantics, spec coherence, wire deltas, catalogs, fixture arms, and house conventions are all clean (explicitly: none).
