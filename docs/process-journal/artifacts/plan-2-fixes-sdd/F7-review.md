## (a) `with_rule_match` no-clobber

Code (`planner.rs:809-828`): `exact`/`substring` deltas now merge via `map.entry(k.clone()).or_insert_with(|| v.clone())` instead of `BTreeMap::extend`; `not` still uses plain `extend`.

**Trace.** For the motivating scenario (rule already has `substring: { track_name: "Foo" }`, candidate proposes `AddSubstring{value:"Director"}` because a matched track's `track_name` tokenizes to `"Director"`): the delta's `substring` map has key `"track_name"`, which already exists on the rule. `or_insert_with` does not fire (key present), so `expr.substring` stays `{"track_name": "Foo"}` unchanged. The candidate is therefore a true no-op: the simulated profile is behaviorally identical to `baseline`'s profile for this rule, so the same two tracks stay ambiguous, `resolves_without_regression`'s `still_ambiguous` check is `true`, and the candidate is rejected before ever reaching `accepted`. Confirmed by direct code trace and by property `matches!` on the emitted `Suggestion::edit` in the new test.

For `exact`: any property already present in `rule.match_expr.exact` cannot generate a *different*-valued candidate in the first place, because `candidates_for_rule` only enumerates values actually observed on tracks that already satisfy the rule's current `exact` map (equality-matched) — so a same-key collision here is always same-value, making the insert-only branch behaviorally moot for `exact` (no lost narrowing opportunity, unlike `substring`, see Minor #2 below).

`not` stays `extend`: appending a `not` sub-expression is monotonically narrowing regardless of duplicates (OR-of-negations only grows), so no collision handling is needed there, and none is applied — correct.

**Independent verification of test hygiene (not vacuous).** Rather than trust the report's stated RED-run transcript, I reverted only `planner.rs` to its pre-fix version (`git show 68ec6aa^:...`), re-ran `cargo test -p muxsmith-core --test suggestions`, and restored via `git checkout --`. Result: exactly the three targeted tests fail, with `with_rule_match_never_widens_an_existing_substring_constraint` failing with the clobber candidate `AddSubstring { value: "Director" }` actually present in the emitted list — reproducing the report's claim independently. With the fix restored, all 5 tests pass again. This confirms the new tests genuinely exercise the bug, not a vacuous pass.

The 2-file fixture (`AMBIGUOUS_FOO` / `GUARDED_FOO`) is the right shape to catch this class of bug: file 2 is already unambiguous under the *original* rule and would be silently misresolved to a decoy track by a clobbering edit, with zero new diagnostics anywhere — the pre-existing "no new diagnostic" acceptance check alone cannot catch this, only the no-clobber merge can. The test asserts both the specific exclusion (`AddSubstring{Director}` never emitted) and the general behavioral property (every *emitted* suggestion, once applied and re-planned, resolves file 2 to track id 1, never the decoy id 2).

**D6 "survives the next dry run" invariant, batch-wide.** `every_suggestion_survives_the_next_dry_run` (single-file, pre-existing) and the new 2-file test both pass; scope of `with_rule_match`/`resolves_without_regression` is unchanged in structure (still per-rule, still batch-replanned via the real `plan_core`), so the invariant is upheld batch-wide, not just per-file.

**Verdict: correct.** No scope creep into candidate generation, ranking, or determinism — diffed `68ec6aa^..68ec6aa` confirms `candidates_for_rule`, `rank_of`, `rank_substring`, `delta_for` are untouched.

## (b) `yaml_fragment` valid, round-trippable YAML

Code (`planner.rs:902-922`): new private `MatchFragment<'a> { #[serde(rename = "match")] expr: &'a MatchExpr }`, and `yaml_fragment` now takes `&MatchExpr` (the actual simulated delta, `cand.apply`) instead of `&StructuredEdit`, serializing via `yaml_serde::to_string`. This also fixes a second, unstated defect beyond quoting: the old code re-derived the fragment from `StructuredEdit`'s `String`-typed `value` field, so a boolean/int candidate (e.g. `forced_track: true`) would have rendered as the string `"true"` regardless; using `cand.apply` preserves the original `Scalar` variant.

**Adversarial round-trip testing (independent).** The shipped test only covers a colon-bearing value. I built a standalone probe (scratch Cargo project depending on the pinned `yaml_serde = "0.10.4"`, same crate/version as `Cargo.lock`) serializing a `Scalar::Str` field through the same untagged-enum shape used in production, then deserializing it back, for 40 adversarial inputs: colon, comma, braces, brackets, `true`/`false`/`yes`/`no`/`null`/`~` (YAML-boolean/null-lookalikes), int-like/float-like strings, leading `-`/`?`/`:`/`&`/`*`/`!`/`%`/`@`/`` ` ``, `|`/`>`, embedded quotes, empty string, leading/trailing whitespace, embedded newline, tab, `#` (mid-string and leading), flow-seq/flow-map-lookalikes, YAML document markers (`---`, `...`), `.nan`/`.inf`, octal/hex-lookalikes, non-ASCII (CJK, emoji). **All 40 round-tripped correctly** — `yaml_serde` (backed by `libyaml-rs`) is type-aware at emit time and quotes exactly the values that need it (e.g. `true`/`false`/`null`/`~`/numeric-lookalikes get single-quoted; `yes`/`no` do not need quoting because this backend's scalar resolution doesn't treat them as booleans — also round-trips fine as a plain string either way). I found no value that breaks the round-trip.

The one thing hand-formatting definitely could not have done (and `yaml_serde` does correctly) is quote a value that looks like another YAML scalar type (`true`, `123`, `null`) so it survives as a string on the way back in — this is exactly the class of bug informally known from `serde_yaml`'s historical "Norway problem"; this crate/version does not have it.

**Verdict: correct**, and more robust than the literal task ask (which named `:`/`,`/`{` as the motivating characters).

## (c) `SuggestionsCapped` diagnostic

Code (`planner.rs:642-650`, `report.rs:139-140`, `diagnostics.ftl:44`, spec table): `total_accepted` captured before `truncate(3)`, `dropped = total_accepted - accepted.len()`, `Diagnostic::info(DiagCode::SuggestionsCapped, "tracks[{ri}].match").with("dropped", ...)` pushed only when `dropped > 0`. Threaded back through `suggest`'s new `(Vec<Suggestion>, Vec<Diagnostic>)` return and `plan_batch`'s `batch.batch_diagnostics.extend(cap_diagnostics)`.

- Severity `Info` — correct, purely advisory, doesn't affect exit code (matches D6: "log the cap ... no silent truncation", not "fail").
- Emitted only when `total_accepted > 3` (since `truncate(3)` only removes when longer) — exactly matches "when >3 candidates were accepted".
- Catalog guard: new variant is picked up automatically by `DiagCode::ALL` (used by `all_keys_are_unique`/`all_keys_match_serde_encoding` and by `muxsmith-cli`'s `catalog_completeness` test, which fails if any `DiagCode` lacks a Fluent entry) — ran `cargo test --workspace`, all green, confirming the Fluent entry is wired correctly.
- CLI wiring confirmed by inspection: `dry_run.rs` already iterates `batch.batch_diagnostics` generically for both human text and `"batch_diagnostics"` JSON output (lines ~104, 139, 213) — no CLI code needed, matching the report's rationale for reusing `Diagnostic` over a bespoke field.
- Spec 5.2 table and rustdoc-per-variant convention both updated in lockstep, preserving the "every DiagCode is exactly one catalog row" invariant `report.rs` documents.
- No `.for_file(...)` on the diagnostic — correct, since the cap is a per-rule, batch-wide fact, not tied to one file (consistent with how other cross-file diagnostics like `DuplicateIdentifier` are modeled as file-less `batch_diagnostics`... actually `DuplicateIdentifier`/`DonorIsPrimary` do carry `.for_file`; `SuggestionsCapped` correctly does not, since unlike those it isn't about one file's plan — no other batch-only, file-less diagnostic exists yet as precedent, but the field is `Option`, and CLI rendering already handles `file: None` for config-time diagnostics, so this is a safe, unsurprising use of an existing code path.)

**Test hygiene, independently reproduced.** Same revert-and-rerun exercise as (a): pre-fix `planner.rs` (which lacks the cap-diagnostic emission entirely, since `suggest` still returned a bare `Vec<Suggestion>`) makes `suggestion_cap_truncation_is_logged_not_silent` fail with "expected a logged suggestion cap for tracks[0]'s conflict" — confirms the test is not vacuous. Post-fix it passes. The test deliberately asserts presence + `dropped > 0` rather than the exact figure (10 accepted for the `P_AMBIGUOUS` fixture); the `dropped` arithmetic itself (`total_accepted - accepted.len()` after `truncate`) is simple enough to verify correct by inspection (no underflow possible, `accepted.len() <= total_accepted` always holds post-truncate).

**Verdict: correct.**

## Findings

Two Minor, purely observational; neither blocks correctness against the F7 task text.

1. **Minor — no test proves `Scalar` type-fidelity through `yaml_fragment` for non-string values.** The report claims (and I verified by static trace, not by a test) that using `cand.apply: &MatchExpr` instead of re-deriving from `StructuredEdit` also fixes boolean/int stringification (`forced_track: true` now serializes as YAML `true`, not `"true"`). No test asserts this — the only fragment-content test (`yaml_fragment_round_trips_a_value_containing_a_colon`) exercises a `Scalar::Str` candidate. Concrete failure scenario a future change could introduce undetected: if `delta_for`'s `AddExact` arm were ever refactored to build its map from `StructuredEdit::AddExact`'s stringified `value` field instead of the passed-in `scalar: &Scalar`, every boolean/int suggestion's `yaml_fragment` would silently regress to quoted-string form (e.g. `forced_track: 'true'`), and nothing in the current suite would catch it. Not required by the F7 task text (which names only `:`/`,`/`{` as the motivating characters, both string-only concerns), so not a defect in the current change — a coverage gap for a claim the report itself makes.
2. **Minor — informational, not a bug.** Once a rule carries any `substring: { track_name: X }` constraint, insert-only-if-absent means *no* future `AddSubstring`/`AddNotSubstring` candidate on `track_name` can ever be accepted for that rule again (the key always collides, so the delta is always a no-op) — this is the correct, safe consequence of "narrow never relax" given the flat one-value-per-key grammar (there is no way to express "AND additionally contains Y" alongside an existing substring constraint in the v1 closed edit grammar). Effect: rules that already have a substring precondition lose access to the substring-based half of candidate generation entirely, falling back to `exact`/`not`-based candidates only. Worth knowing if suggestion coverage for such rules looks thinner than expected in practice; not something this fix should have handled differently, since the alternative (allowing a second substring value in some other form) is out of the closed grammar's v1 scope.
