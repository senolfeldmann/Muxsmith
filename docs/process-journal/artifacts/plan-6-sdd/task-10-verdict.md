### Adjudications

**Q1 — Harness-config fix: CORRECT, and correctly handled as brief-defect-adapted-and-surfaced.**
(a) The added `define: { "process.env.NODE_ENV": JSON.stringify("production") }` (`vite.mount.config.ts:19-21`) is the standard documented Vite recipe. The sibling `vite.harness.config.ts` has no `plugins: [vue()]`, no `define`, and `emptyOutDir: true` — it bundles only `@tauri-apps/api`, which carries no `process.env` reference, so it genuinely never needed it. The mount config bundles Vue's esm-bundler build, which leaves `process.env.NODE_ENV` for the consuming bundler to define; `build.lib` does not auto-substitute it. The claim is verified, not borrowed.
(b) This is the house `brief-drafts-verified-against-tree` pattern (`process-conventions.yaml:361`: "divergences are adapted and SURFACED in the report, never transcribed or silently resolved"), executed exactly — same mechanism, a mechanical build-config correction, found by running it, disclosed with the empirical evidence (bundle 430→247 kB on the fix). Not a design fork; no routing owed.

**Q2 — Catalog-key reuse: acceptable-on-merits but NEEDS OWNER ROUTING.**
(a) Semantic fit, both locales judged on the actual strings: EN `Add`/`Drop` (`en/gui-editor.ftl:73-74`), DE `Hinzufügen`/`Verwerfen` (`de/gui-editor.ftl:75-76`). `Add`/`Hinzufügen` are clean generic captions. `Drop` reads as remove within this app's own `KEEP_DROP` vocabulary, so it is defensible; the weakest link is German `Verwerfen` ("discard/reject") as a per-row remove button, where `Entfernen`/`Löschen` is the conventional word — `Verwerfen` carries a "discard my changes" connotation. Acceptable, not ideal. The stronger structural concern is the **key name**: `editor-attachment-rule-add`/`-drop` is domain-scoped, now captioning `trackRule.changes` and `matchExpr` list buttons — a latent coupling (an AttachmentRule-specific rewording later silently changes every list/map button).
The implementer's absence-claim is verified: those two keys are the *only* generic add/drop values in any catalog, the 43-key budget is a closed owner ruling, and `.ftl` is out of task scope — so reuse was the only in-budget path, and cross-view key reuse is an established house pattern (`browse-button` in `gui-common.ftl`, reused by `SettingsDialog`/`BatchView`/`FirstRun`). On the merits the choice is reasonable and was disclosed prominently (report:475-484).
(b) **Not within remit.** `process-conventions.yaml:323` is categorical: "routing by fork nature: product-scope or **user-visible behavior -> the governing human, always**." Button wording is user-visible behavior; the brief left the dimension open (silent on how list/propertyMap source add/remove text); Task 12 will scale this across every list/map instance. Per the rule it should have returned as NEEDS_CONTEXT and been routed **before** resolution, not resolved-then-disclosed. **The controller should route this to Şenol** before Task 12 bakes it in — decide once between (i) keeping the reuse, or (ii) a deliberate later `gui-editor.ftl` amendment adding 2-4 genuinely generic keys. The widget code itself is fine and reversible (one string in two places); it is the *decision* that needs the owner.

**Q3 — String-typed propertyMap: real UX gap, acceptable-with-tracking. NOT Critical; nothing reaches a mux run silently.**
(a) Traced end to end. The widget holds `Record<string, string>` and `setValue` writes the raw string (`PropertyMapWidget.vue`), so typing into a boolean property's cell lands `{ forced: "true" }` — a `Scalar::Str("true")` after deserialization, where `forced` is `PropType::Boolean`. Core catches it: `validate_changes` (`validate.rs:374-393`) runs `scalar_fits` (`:416-425`), which has no `(Str, Boolean)` arm, and emits an **`error`-severity `ValueTypeMismatch`** ("expected Boolean, found string"). So it is *not* a silent Str-where-Bool at the validation layer. Through the GUI the model is honest and the spec-7 "disable Save while errors exist" affordance (Task 12/13) blocks saving/running such a profile.
(b) **Not Critical, not a Task-10 defect.** No run path exists from Task 10 at all (widgets aren't mounted until Task 13). It is a genuine **UX gap**: because every value is a string, `forced`/`default` — the most common `changes` case — are *unenterable as valid booleans*, so the user hits a permanent `ValueTypeMismatch` with no way forward until Task 12/13 add per-value scalar typing. This is exactly the shape the house ledger already flagged as runtime-failing (`process-conventions.yaml:335`, the D49 entry: "`Scalar::Str("true")` where the engine emits `Scalar::Bool(true)` — it compiles and fails at runtime"). Correctly disclosed (report:485-492). Track for Task 12/13; Important for the forward path, not blocking here.
One honest scoping note: the mux gate is per-file `plan.is_some()` (`run.rs:304-321`, `finalize_plans` `planner.rs:1319-1324`), and a `changes` `ValueTypeMismatch` is a profile-level `config_diags` entry — `resolve_changes` carries non-`language` settables through unchecked (`planner.rs:813-849`), so at the *core/CLI* level a hand-edited profile with this error would still plan and `value_str` would emit `--forced-track <tid>:true` (`command.rs:241-248`). That is pre-existing core behavior outside this task and depends on the GUI Save-disable gate for the frontend path; it is not introduced by Task 10, and I did not exercise mkvmerge's tolerance of `true` vs `1`.
